# Windows-профиль с кириллицей в имени: где ломается и как лечить

Знание для того, кто пишет или запускает скрипты агента на Windows-машине оператора, у
которого имя профиля написано кириллицей (`C:\Users\<Имя Фамилия>`). Один корень даёт целое
семейство поломок, и почти все они **молчаливые**: скрипт не падает, а честным голосом
сообщает неправду («файл не найден», «docker не отвечает», «возражений нет»).

## Корень

Три слоя по-разному понимают байты пути и вывода:

- **Python** на Windows пишет stdout в кодовой странице консоли (`cp1251` или `cp1252`), а
  не в UTF-8. Bash, читающий этот вывод, ждёт UTF-8.
- **Git Bash (msys)** переводит пути профиля сам и ломает их для `ssh`: `~/.ssh/config` и
  `known_hosts` не находятся.
- **PowerShell** читает файлы в системной кодировке и пишет BOM; рабочая копия git при
  `core.autocrlf=true` хранится с CRLF.

## Поломки и лечение

| Симптом | Причина | Лечение |
|---|---|---|
| bash-скрипт говорит «не найден» про существующий файл, путь в сообщении с `?` или `�` | python напечатал путь в cp1251 | `export PYTHONIOENCODING=utf-8` в шапке **каждого** bash-скрипта, который читает вывод python |
| хук молча пропускает то, что должен блокировать, код 0 | python упал с `UnicodeEncodeError` на русском тексте | та же строка в шапке хука |
| `ssh <алиас>` из Git Bash: `Could not resolve hostname` / `Host key verification failed` | msys не видит `~/.ssh/config` | параметры алиаса — в PowerShell `ssh -G <алиас>`; временная обёртка `ssh` в scratchpad сессии: `-i` копия ключа, `UserKnownHostsFile` — строки по IP из `known_hosts`, `StrictHostKeyChecking=yes`; после работы удалить; не класть в корень диска |
| скилл без адреса сервера «проверил» ноутбук | обёртку не собрали, адрес не передали | health-check без `SSH_TARGET` на не-Linux отказывает с кодом 3; цель передавать всегда явно |
| скрипт на сервер из PowerShell: первая строка `command not found`, кириллица кракозябрами | BOM + CRLF + чтение не в UTF-8 | `Get-Content -Raw -Encoding UTF8 f \| ssh <хост> "tr -d '\r' \| sed '1s/^\xEF\xBB\xBF//' \| bash -s"` |
| JSON-конфиг «не разбирается» или «поля нет», хотя поле есть | BOM в начале файла | читать с `encoding="utf-8-sig"` |
| shellcheck SC1017 «Literal carriage return» во всех строках | `core.autocrlf=true`: рабочая копия в CRLF, в git уходит LF | шум, не дефект правки; размеры для бюджета мерить через `tr -d '\r'` |

## Как проверять, что защита действительно есть

Свой `export PYTHONIOENCODING=utf-8` в тесте лечит проверяемый скрипт за него: переменная
наследуется, и тест остаётся зелёным, даже если защиту из скрипта убрать (поймано
28.08.2026, см. [`building-enforcement.md`](building-enforcement.md)). Поэтому чужая
кодировка навязывается **именно проверяемому скрипту**: `env PYTHONIOENCODING=cp1251 bash
<скрипт>`, плюс путь с русскими именами во временном дереве. Так дефект воспроизводится и на
Linux/macOS, а не только на машине оператора. Образцы: секция [7] `test-red-zone-guard.sh`,
секция [8] `scripts/test-host-digest.sh`.

## Правило при написании нового скрипта

Пишешь bash, в котором есть `python3` и его вывод идёт дальше в скрипт, — строка
`export PYTHONIOENCODING=utf-8` в шапке и тест с навязанной cp1251. Видишь в выводе
скрипта «не найден» с искажённым путём — сначала кодировка, а уже потом «файла нет».
